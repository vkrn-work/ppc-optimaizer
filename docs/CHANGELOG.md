# Changelog — PPC Optimizer

Все значимые изменения фиксируются здесь в обратном хронологическом порядке.
Формат: `[версия] — дата — краткое описание`. Детали под каждой записью.

---

## [1.4.0] — 2026-07-18

### Главное

Полный пайплайн (сбор → CRM-импорт → ИИ-анализ → предложение → approve → apply →
реальная запись в Яндекс Директ) впервые прогнан end-to-end на реальном кабинете
с реальным API-ключом (Groq) и подтверждён ответом Yandex Direct API. До этой версии
уровни 2–3 существовали в коде, но никогда не запускались вживую — прогон вскрыл
несколько ранее незамеченных багов, все они исправлены и проверены.

### Исправлены баги

**Celery — задачи молча не выполнялись без единой ошибки**

`celery_app.py` не содержал `task_routes` для большинства задач (`run_llm_analysis`,
`apply_suggestion` и др.) — они уходили в очередь Celery по умолчанию (`celery`),
которую worker не слушает (`-Q default,analysis`). Задача принималась, ничего не
падало, но она никогда не выполнялась — ни ошибок, ни логов. Добавлен явный
`task_routes` для каждой задачи в проекте.

**Approve предложения падал с «Failed to fetch»**

Таблица `hypotheses` в реальной БД была создана до того, как в модель добавили поля
`description`, `change_description`, `forecast`, `object_type`, `object_id`, `source`
(и до того, как `suggestion_id` стал nullable) — `create_all()` не добавляет колонки
в уже существующие таблицы. Approve падал с `UndefinedColumnError`, что роняло
бэкенд без CORS-заголовков — на фронте это выглядело как обычный сетевой сбой.
Добавлены idempotent `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` в `_run_migrations()`.

**Apply падал с «Failed to fetch» — модуль записи в Директ отсутствовал**

`app/collectors/direct_writer.py` был указан в импортах, но никогда не существовал
в репозитории — `_apply_suggestion_async()` падал с `ImportError` при первом вызове.
Написан модуль целиком: `set_keyword_bid()`, `add_negative_keywords()` (с чтением
текущего списка через `adgroups.get` и слиянием — `NegativeKeywords.Items` в
`adgroups.update` полностью заменяет список, а не дополняет его), `suspend_keyword()`.

**Неверные имена ключей в ответе Yandex Direct API v5**

Первая версия `direct_writer.py` ожидала `KeywordsUpdateResults`/`AdGroupsUpdateResults`
(по аналогии с именем сервиса) — реальный API возвращает результат `.update`-вызова
под ключом `UpdateResults` независимо от сервиса (keywords/adgroups/campaigns/...).
Apply завершался с «пустой ответ AdGroupsUpdateResults», хотя запрос в Директ
проходил успешно. Исправлено чтение на `result.get("UpdateResults", [])`.

**Минус-слова с ведущим дефисом отклонялись Директом (ошибка 5002)**

Модель иногда возвращала минус-слова уже с «-» в начале (скопировав формат из
датасета, где минус-фразы ключей хранятся с дефисом) — Yandex Direct API отклоняет
такие значения («Знак '-' нельзя использовать в начале и в конце слов»). Добавлена
двухуровневая защита: санитайзер `_clean_negative_word()` в `direct_writer.py`
(снимает ведущие/хвостовые `-`/`+`) и явная инструкция в system-промпте/схеме
`llm_providers.py` — модель должна отдавать голое слово без дефиса.

**`suggestions.js` не был подключён к реальному пайплайну approve/apply**

Страница читала `analysis.problems`/`analysis.opportunities` — устаревший формат
rule-based анализатора, у LLM-предложений его нет, поэтому список всегда был пуст.
Кнопка «Взять в работу» вызывала `createHypothesis()`, а не реальный approve.
Страница переписана: вкладки по статусу (pending/approved/applied/rejected),
реальные вызовы `api.actionSuggestion()` (accept/reject) и `api.applySuggestion()`.

### Добавлено — safety-ограничение `bid_editable`

Выяснилось эмпирически (на реальном кабинете «ГТО 4»): ставка ключевого слова
редактируется через Yandex Direct API (`keywords.update`, поле `Bid`) только для
кампаний на стратегии `MANUAL_CPC`. Для автостратегий/ЕПК API отклоняет запрос
целиком («8000: неизвестный параметр Bid») — это ограничение API, не системы;
в этом конкретном кабинете таких кампаний 0 из 89.

Принято решение (по явному запросу пользователя): не пытаться применить и не
предлагать такие изменения вовсе, а учить модель не генерировать их для
нередактируемых кампаний. Реализовано в двух местах:
- `llm_analyzer.py._build_dataset()` — джойнит Keyword → AdGroup → Campaign,
  добавляет в каждую строку датасета `bid_editable: bool` (True только для
  `strategy_type == 'MANUAL_CPC'`)
- `llm_analyzer.py._validate_change()` — жёстко отклоняет `bid_raise`/`bid_lower`
  при `bid_editable=False` на сервере, независимо от того, следует ли модель
  инструкции в промпте; `llm_providers.py` также содержит мягкую инструкцию
  в system-промпте с объяснением, что предлагать вместо ставки
  (`add_negatives`/`pause`/`ad_rewrite`/`ad_test`)

### Известные ограничения

- Из 4 LLM-провайдеров end-to-end на реальном ключе проверен только Groq. Gemini,
  OpenRouter и Claude используют ту же общую логику вызова (`llm_providers.py`),
  но не были прогнаны вживую в этой сессии — при первом реальном запуске возможны
  нюансы формата ответа, см. `/llm-debug`
- `oauth_token` хранится в открытом виде в БД — нужно шифрование (запланировано)
- В этом конкретном кабинете 0 кампаний на `MANUAL_CPC` (9 на `AUTO`, 80 без
  определённого типа — вероятно ЕПК, коллектор их пока не классифицирует) — то
  есть `bid_raise`/`bid_lower` сейчас структурно не могут быть применены ни для
  одного ключа в этом кабинете; работают только `add_negatives`, `pause`,
  `ad_rewrite`, `ad_test`

## [1.3.0] — 2026-07-18

### Главное

Добавлен выбор LLM-провайдера для ИИ-анализа. Раньше `run-llm-analysis` был
жёстко привязан к Claude (платный, без постоянного бесплатного тарифа) — теперь
можно выбрать Gemini, Groq или OpenRouter и прогнать весь пайплайн бесплатно,
без карты, а на Claude переключиться только когда логика подтверждена.

### Добавлено

**`app/analyzers/llm_providers.py` — новый модуль**

Единая точка вызова 4 провайдеров с общей JSON-схемой результата (`{"changes": [...]}`)
и одним system-промптом:

| Провайдер | Механизм | Стоимость |
|---|---|---|
| Claude | `tool_use` (Anthropic SDK) | платный |
| Gemini | structured output (`response_schema`), без function calling — надёжнее для бесплатной модели | бесплатно |
| Groq | OpenAI-совместимый `tool_choice` (function calling) | бесплатно |
| OpenRouter | OpenAI-совместимый `tool_choice` (function calling) | бесплатные модели |

**`llm_analyzer.py`** — `generate_suggestions()` и `_call_llm()` принимают параметр
`provider`, вызов делегируется в `llm_providers.call_llm()`. Провайдер и модель
сохраняются в `analysis.summary` — видно на странице «ИИ: вход/выход».

**`routes.py`**
- `GET /llm-providers` — список провайдеров и их доступность (настроен ли ключ
  в `.env`) для селектора на фронте
- `POST /accounts/{id}/run-llm-analysis?provider=...` — принимает провайдера
  query-параметром, по умолчанию `claude`

**`core/config.py`** — новые переменные: `GEMINI_API_KEY` / `GEMINI_MODEL`,
`GROQ_API_KEY` / `GROQ_MODEL`, `OPENROUTER_API_KEY` / `OPENROUTER_MODEL`

**Фронтенд (`crm-import.js`)** — кликабельный селектор моделей над кнопкой
запуска. Провайдеры без настроенного ключа — затемнены и заблокированы для
клика, кнопка запуска показывает выбранного провайдера. Если ни один ключ не
настроен — предупреждение с подсказкой взять бесплатный у Gemini/Groq/OpenRouter.

**`llm-debug.js`** — в списке анализов и в деталях суммаризации теперь виден
провайдер, которым был выполнен конкретный запуск.

### Известные ограничения (сняты в 1.4.0)

- Ни один из 4 провайдеров не был вызван с реальным API-ключом в среде разработки
  (нет исходящего сетевого доступа из песочницы). Запросы собраны по документации
  каждого провайдера, но не проверены вживую — на реальном ключе возможны нюансы
  формата ответа. **Обновление 1.4.0:** Groq проверен end-to-end на реальном
  кабинете и ключе, полный пайплайн включая apply работает.
- requirements.txt не менялся — Gemini/Groq/OpenRouter вызываются через уже
  использовавшийся `httpx`, отдельные SDK не добавлялись.

## [1.2.0] — 2026-04-21

### Главное

Реализован Уровень 2–3 пайплайна: импорт заявок из CRM, ИИ-анализ через Claude
API и запись подтверждённых изменений напрямую в Яндекс Директ. До этой версии
у suggestions был только rule-based источник (`cr_analyzer.py`) и не было способа
применить одобренное предложение в кабинете — только approve/reject в БД без
реального эффекта.

### Добавлено

**`app/analyzers/llm_analyzer.py` — новый модуль**

Агрегирует `keyword_stats` + `leads` (CRM) в компактный датасет по ключевым
словам, отправляет в Claude API через `tool_use` со строгой JSON-схемой ответа,
валидирует полученные изменения по safety-лимитам перед записью в `suggestions`:
- запрет менять ставку более чем на `MAX_BID_CHANGE_PCT` (50%) за раз
- потолок ставки `MAX_BID_ABSOLUTE_RUB` (3000₽)
- дедупликация — повторный сигнал для уже существующего pending-предложения
  не создаёт дубликат
- в `analysis.summary` сохраняется и то, что отправили модели, и сырой ответ — видно на
  фронте для отладки и проверки доверия к результату

**`app/importers/crm_importer.py` — новый модуль**

Парсит CSV/XLSX-выгрузку заявок (1С, amoCRM, Bitrix24 и т.п.): автоопределение
кодировки (utf-8/utf-8-sig/cp1251) и разделителя, сопоставление колонок по
алиасам на русском и английском (`utm_term`/`ключевое слово`/`keyword` и т.п.),
матчинг лида с ключевым словом по фразе. Записывает в таблицу `leads`.

**`app/collectors/direct_writer.py` — новый модуль**

Write-операции в Яндекс Директ API v5, отдельно от read-only `direct_collector.py`:
`bids.set` (ставки), `adgroups.update` (минус-слова на уровне группы),
`keywords.suspend`/`resume` (пауза/возобновление), `ads.update` (заголовки).
Каждый метод возвращает `(success, detail)` без исключений наружу.

**`routes.py` / `core/tasks.py`**
- `POST /accounts/{id}/run-llm-analysis` — запуск ИИ-анализа
- `POST /accounts/{id}/crm-import` — загрузка файла CRM
- `POST /suggestions/{id}/apply` → `_apply_suggestion_async()` — применяет
  только предложения в статусе `approved`, с повторной проверкой типа изменения
  и парсингом значения перед вызовом `direct_writer`

**БД — новые колонки (авто-применяются при старте через `_run_migrations()`,
ручной SQL не требуется)**

- `keyword_stats.weighted_impressions`, `weighted_ctr` — взвешенные показы/CTR
  из Директа (`WeightedImpressions`/`WeightedCtr`), корректнее сравнивать при
  разных позициях показа
- `keyword_stats.bounce_rate` — отказы по клику из Директа
- `keyword_stats.sessions` — визиты из Метрики, обогащается по
  `utm_term → keyword.phrase` после каждого сбора
- `campaigns.epk_collapse_detected` — флаг ЕПК-обвала
- `hypothesisverdict` enum: добавлено значение `neutral`
- таблица `leads` — создаётся автоматически через `Base.metadata.create_all()`

**Коллектор (`direct_collector.py`)** — в `CRITERIA_PERFORMANCE_REPORT` добавлены
поля `WeightedImpressions`, `WeightedCtr`, `BounceRate`.

**Фронтенд** — новые страницы `crm-import.js` (загрузка файла + запуск ИИ-анализа)
и `llm-debug.js` (просмотр входа/выхода модели), кнопка Apply на `suggestions.js`.

### Исправление к этой записи (2026-07-18)

Предыдущая версия этой записи в CHANGELOG ошибочно описывала переработку
`cr_analyzer.py` на движок из 12 сигналов (S-001…S-043 и т.д.) — этого кода
в проекте нет, `cr_analyzer.py` остался без изменений (топологический движок
 v4.1, тот же, что и раньше). Запись исправлена на то, что реально было
реализовано в этой версии: LLM-анализатор, CRM-импорт, запись в Директ.

### Известные ограничения (сняты в 1.4.0)

- `oauth_token` хранится в открытом виде в БД — нужно шифрование (запланировано)
- Сигналы поведенческого анализа в `cr_analyzer.py` требуют данных Метрики —
  при первом запуске до сбора снапшота часть сигналов не генерируется
- Матчинг `utm_term → keyword` в CRM-импорте приближённый (по фразе), точный
  требует client_id/roistat_id
- Реального OAuth-флоу подключения кабинета нет — токен вставляется вручную
  в Настройках после того, как получен на oauth.yandex.ru
- ~~LLM-анализ и запись в Директ не были проверены на реальном кабинете и с
  реальными ключами~~ — проверено в 1.4.0

## [1.1.0] — 2026-04-20

### Исправлены баги

**Бэкенд**

- `tasks.py` — исправлен критический баг: `is_active` у кампаний выставлялось через `Status == "ON"`, хотя поле `Status` в API Директа означает статус модерации (ACCEPTED/REJECTED), а не статус запуска. Поскольку запрос уже фильтрует `States: ON` и `Statuses: ACCEPTED`, все пришедшие кампании активны — теперь явно проставляется `is_active=True`. Это устраняло показ 87 кампаний вместо реального числа.
- `tasks.py` — `AvgEffectiveBid` из Reports API приходит в микрорублях (1 руб = 1 000 000 мкруб). Добавлено деление на `1_000_000` при сохранении в `avg_bid`. До этого ставки в таблице ключей были завышены в миллион раз.
- `tasks.py` — `strategy_type` теперь сохраняется при upsert кампаний (раньше поле не попадало в `set_` при конфликте).
- `routes.py` — `avg_cpc` в агрегациях теперь считается как `sum(spend)/sum(clicks)`, а не `avg(avg_cpc)`. Аналогично `ctr` = `sum(clicks)/sum(impressions)*100`. Среднее от средних некорректно при разном объёме кликов.
- `routes.py` — в ответе `/campaigns` добавлено поле `direct_id` (ID кампании в Яндекс Директ). Поле было в БД, но не передавалось на фронтенд.
- `routes.py` — диагностика (`/diagnostics`) переписана: убран `__import__` через eval-подобный вызов, счётчик поисковых запросов теперь работает корректно.

**Фронтенд**

- `api.js` — добавлены недостающие методы, из-за отсутствия которых страницы Корректировки и Диагностика падали с `TypeError: api.X is not a function`:
  - `getMetrikaSnapshot(id)`
  - `getDiagnostics(id)`
  - `createHypothesis(id, data)`
  - `getSearchQueries(id, params)`
  - `getAdGroups(id, campaignId)`
  - `triggerHistoricalSync(id, days)`
- `api.js` — `getDashboard` и `getCampaigns` теперь принимают параметр `period`. Раньше переключение периода на дашборде и в кампаниях не имело эффекта.
- `Layout.js` — время последней синхронизации теперь корректно показывает МСК. `last_sync_at` из БД приходит как UTC без суффикса `Z` — браузер трактовал это как локальное время. Добавлено принудительное добавление `Z` перед конвертацией.
- `bids.js` — убран жёсткий фильтр `strategy_type === 'MANUAL_CPC'` на список кампаний. Теперь показываются все кампании, ручные помечаются `✎`, автоматические `⚙`.
- `bids.js` — добавлен выбор группы объявлений (появляется после выбора кампании, подгружает группы через новый эндпоинт).
- `bids.js` — добавлены столбцы CTR и CPC в таблицу ключей.

### Добавлено

- `routes.py` — новый эндпоинт `GET /accounts/{id}/ad-groups` — возвращает группы объявлений с базовой статистикой (клики, расход, количество ключей) за выбранный период.
- `routes.py` — эндпоинт `POST /accounts/{id}/sync` теперь принимает query-параметр `?days=N`. По умолчанию 28 дней (стандартный цикл), при `days=90` собирает ретроспективу. Позволяет загрузить историю без ожидания накопления данных.
- `tasks.py` — `collect_account_data` принимает параметр `days: int = 28`, который передаётся в async-функцию сбора. Включена детальная логика: `logger.info` на каждом этапе (кампании, группы, ключи, статистика).
- `api.js` — метод `triggerHistoricalSync(id, days=90)` для запуска ретроспективного сбора через UI.

### Известные ограничения (без изменений)

- `oauth_token` хранится в открытом виде в БД — нужно шифрование (запланировано).
- Страница групп объявлений в разделе "По кампаниям" не реализована — только кампании и ключи.
- Уровень 2 (CRM/лиды) не реализован — блок CRM на дашборде показывает заглушку.

## [1.0.0] — 2026-04 (первоначальный деплой)

MVP задеплоен на Railway. Реализован Уровень 1: сбор данных из Яндекс Директ и Метрики, CR-анализ, дашборд с KPI и дельтами, 11 страниц фронтенда.
