# Деплой на Railway — пошаговая инструкция

Время: ~20 минут (+5 минут на ключ LLM). Результат: рабочий дашборд по публичной ссылке
со сбором статистики, ИИ-анализом и записью изменений в Директ — весь пайплайн проверен
end-to-end на реальном кабинете.

---

## Шаг 1 — Загрузить код на GitHub

1. Зайти на https://github.com и создать аккаунт (если нет)
2. Нажать **New repository** → назвать `ppc-optimizer` → **Create repository**
3. На своём компьютере:

```bash
# Распаковать zip
unzip ppc-optimizer.zip
cd ppc-optimizer

# Инициализировать git и загрузить
git init
git add .
git commit -m "Initial commit"
git branch -M main
git remote add origin https://github.com/ВАШ_ЛОГИН/ppc-optimizer.git
git push -u origin main
```

> Если git не установлен: https://git-scm.com/downloads

---

## Шаг 2 — Создать проект на Railway

1. Зайти на https://railway.app
2. **Sign in with GitHub** (авторизуйтесь через GitHub-аккаунт)
3. Нажать **New Project**
4. Выбрать **Deploy from GitHub repo** → выбрать `ppc-optimizer`

---

## Шаг 3 — Добавить PostgreSQL

1. В проекте нажать **+ New** → **Database** → **Add PostgreSQL**
2. Railway автоматически создаст базу и добавит переменную `DATABASE_URL`
3. Запомните: нажать на PostgreSQL → вкладка **Variables** → скопировать `DATABASE_URL`

---

## Шаг 4 — Добавить Redis

1. Нажать **+ New** → **Database** → **Add Redis**
2. Railway создаст Redis и добавит `REDIS_URL`

---

## Шаг 5 — Настроить бэкенд

1. В проекте Railway нажать на сервис из GitHub (он создался автоматически)
2. Вкладка **Settings** → **Root Directory** → написать `backend`
3. Вкладка **Variables** → добавить переменные:

```
YANDEX_CLIENT_ID        = (ваш ID приложения Яндекс)
YANDEX_CLIENT_SECRET    = (ваш секрет приложения Яндекс)
SECRET_KEY              = (любые 32 случайных символа, например: abc123xyz...)
ENVIRONMENT             = production
ALLOWED_ORIGINS         = https://ДОМЕН_ФРОНТЕНДА.up.railway.app
```

> DATABASE_URL и REDIS_URL Railway подставит автоматически из добавленных баз.

4. Вкладка **Settings** → **Deploy** → Start Command:
```
uvicorn app.main:app --host 0.0.0.0 --port $PORT
```

5. Нажать **Deploy** → дождаться зелёного статуса

---

## Шаг 5.5 — Ключ для ИИ-анализа (обязательно для run-llm-analysis)

Без хотя бы одного из этих ключей кнопка «Запустить ИИ-анализ» на странице
crm-import вернёт ошибку 400 «API-ключ не настроен». Провайдер выбирается
на фронте перед запуском, ключ нужен только для того, что реально собираетесь
использовать — остальные переменные можно оставить пустыми.

Добавьте в **Variables** бэкенд-сервиса (тот же список, что и в шаге 5):

| Провайдер | Переменные | Стоимость | Где взять ключ |
|---|---|---|---|
| Claude | `ANTHROPIC_API_KEY` | платный, нет постоянного free-тарифа | https://console.anthropic.com/settings/keys |
| Gemini | `GEMINI_API_KEY` | бесплатно, без карты | https://aistudio.google.com/apikey |
| Groq | `GROQ_API_KEY` | бесплатно, без карты | https://console.groq.com/keys |
| OpenRouter | `OPENROUTER_API_KEY` | бесплатные модели без карты | https://openrouter.ai/keys |

Модель для каждого провайдера задаётся отдельной переменной (необязательно,
есть дефолт): `ANTHROPIC_MODEL`, `GEMINI_MODEL`, `GROQ_MODEL`, `OPENROUTER_MODEL`.

**Рекомендация для первого теста:** начните с Gemini или Groq — это бесплатно
и без карты, проверите весь пайплайн (сбор → CRM → анализ → предложения → apply) не
потратив ни рубля, и только потом подключите Claude, если результат устроит.

> ✅ Пайплайн с провайдером Groq проверен end-to-end на реальном кабинете и реальном
> ключе: анализ → предложение → approve → apply → подтверждённое изменение в кабинете
> Яндекс Директ. Gemini, OpenRouter и Claude реализованы по той же общей схеме вызова
> (`llm_providers.py`), но не были прогнаны на реальном ключе в этой сессии — если
> парсинг ответа не сработает, сырой ответ модели и текст ошибки видны на странице
> «ИИ: вход/выход» (`/llm-debug`).

## Шаг 6 — Добавить Celery worker

1. В проекте нажать **+ New** → **GitHub Repo** → тот же репозиторий
2. **Settings** → **Root Directory** → `backend`
3. **Settings** → Start Command:
```
celery -A app.core.celery_app worker --beat --loglevel=info -Q default,analysis
```
4. **Variables** → добавить те же переменные что в шагах 5 и 5.5
   (DATABASE_URL и REDIS_URL — снова добавить вручную, скопировав из баз)
5. Deploy

> ⚠️ Очередь worker'а (`-Q default,analysis`) должна включать все очереди, на которые
> роутятся задачи в `celery_app.py` (`task_routes`). Если добавляете новую фоновую задачу —
> обязательно пропишите для неё очередь в `task_routes` и убедитесь, что worker её слушает.
> Задача, не попавшая ни в `task_routes`, ни в список очередей worker'а, уходит в очередь
> `celery` по умолчанию, которую никто не слушает — она просто зависает без единой ошибки
> в логах. Это самая коварная категория проблем в этом проекте — см. `docs/CHANGELOG.md` 1.4.0.

## Шаг 7 — Добавить фронтенд

1. **+ New** → **GitHub Repo** → тот же репозиторий
2. **Settings** → **Root Directory** → `frontend`
3. **Variables**:
```
NEXT_PUBLIC_API_URL = https://ДОМЕН_БЭКЕНДА.up.railway.app
```
4. Start Command: `node .next/standalone/server.js`
5. Deploy

---

## Шаг 8 — Получить ссылки

Для каждого сервиса: **Settings** → **Networking** → **Generate Domain**

Вы получите три ссылки вида:
- Бэкенд: `https://ppc-optimizer-backend-xxxx.up.railway.app`
- Фронтенд: `https://ppc-optimizer-frontend-xxxx.up.railway.app`

Обновите переменную `ALLOWED_ORIGINS` в бэкенде на реальный домен фронтенда.
Обновите `NEXT_PUBLIC_API_URL` во фронтенде на реальный домен бэкенда.

---

## Шаг 9 — Первый вход

1. Открыть ссылку фронтенда
2. Добавить кабинет: логин Яндекс + OAuth-токен + целевой CPL
3. Нажать **↻ Собрать данные**
4. Через 5–10 минут появятся кампании, ключи и предложения
5. На странице **CRM-импорт**: загрузить выгрузку, выбрать доступного провайдера
   (недоступные без ключа — затемнены), нажать **Запустить ИИ-анализ**
6. Проверить результат на странице **ИИ: вход/выход** — что отправили модели
   и что она вернула, включая ошибки парсинга, если есть
7. На странице **Предложения**: approve/reject → **Apply** — изменение уйдёт
   в Директ. Проверить, что оно реально применилось, в самом кабинете Директа.

## Как получить OAuth-токен Яндекс

1. https://oauth.yandex.ru → **Создать приложение**
2. Платформа: **Веб-сервисы**
3. Права: отметить `direct:api` и `metrika:read`
4. Callback URI: `https://oauth.yandex.ru/verification_code`
5. Создать → нажать **Получить токен** → скопировать токен

> Для шага 9.7 (запись изменений в кабинет через Apply) токену нужны полные
права на `direct:api`, а не только чтение отчётов — если создавали токен
раньше только для сбора статистики, лучше выпустить новый и указать его
в Настройках кабинета.

$5 free credits в месяц. При 3 сервисах (бэкенд + worker + фронтенд) + 2 базах:
- Приблизительный расход: ~$3–4/мес при умеренном использовании
- Для тестирования хватит на 1–2 месяца бесплатно
- Когда перейдёте на Hetzner — просто поменяете `deploy.sh`

## Если что-то пошло не так

```
# Посмотреть логи — в Railway: сервис → вкладка Logs

# Частые проблемы:
# 1. "relation does not exist" / "column does not exist" — БД не в актуальной схеме
#    Решение: перезапустить бэкенд (Deploy → Redeploy) — миграции в _run_migrations()
#    выполняются автоматически при каждом старте и идемпотентны (ADD COLUMN IF NOT EXISTS)

# 2. "Connection refused redis" — REDIS_URL не добавлен в worker
#    Решение: добавить переменную REDIS_URL в Variables воркера

# 3. CORS error / "Failed to fetch" в браузере — либо ALLOWED_ORIGINS не совпадает
#    с доменом фронтенда, либо (чаще) бэкенд упал с 500 на самом запросе и не вернул
#    CORS-заголовки вовсе. Смотрите Logs бэкенда за тот момент — обычно там видна
#    настоящая причина (например, отсутствующая колонка в БД или несуществующий модуль)

# 4. "API-ключ для 'X' не настроен на сервере" при запуске ИИ-анализа
#    Решение: добавить соответствующую переменную из шага 5.5 и передеплоить бэкенд

# 5. Задача поставлена в очередь, но ничего не происходит — ни в БД, ни в логах worker'а
#    Решение: проверить, что имя задачи есть и в task_routes (celery_app.py), и что
#    worker слушает эту очередь (-Q default,analysis в Start Command). См. Шаг 6.

# 6. Apply возвращает "API error 8000: неизвестный параметр Bid"
#    Это не баг — кампания использует автостратегию/ЕПК, а не MANUAL_CPC.
#    Yandex Direct API принимает поле Bid на уровне ключевого слова только для
#    кампаний на ручном управлении ставками. Для остальных кампаний система сама
#    не предложит bid_raise/bid_lower (см. bid_editable в README) — если такое
#    предложение всё же появилось для старого анализа, отклоните его.

# 7. Apply возвращает "Direct API errors" / "пустой ответ" — обычно означает, что у
#    OAuth-токена нет прав на запись, либо значение не прошло валидацию самого Директа
#    (например, минус-слово с ведущим дефисом). Решение: перевыпустить токен с полным
#    доступом direct:api, проверить лимиты в Настройках кабинета.
```
